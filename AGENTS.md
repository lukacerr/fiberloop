# FiberLoop Project Guide

## Project Mission

This codebase is for building presentation and product mocks for FiberLoop, a climate-tech concept for reducing microplastic pollution caused by washing and drying synthetic clothing.

FiberLoop targets microfibers released by textiles such as polyester, nylon, acrylic, and elastane. The product concept combines a filtration cartridge installed near the washing machine drain or dryer ventilation path, IoT sensors for flow and saturation, a mobile app, QR-based cartridge tracking, municipal collection points, rewards, and aggregate environmental metrics.

The work in this repo is not a production product. It is a polished static demo for a university presentation, designed to explain the problem, sell the solution, and show how the mobile experience could work.

## Non-Negotiable Constraints

- Build static Astro output only: HTML, CSS, and JS in `dist/`.
- Do not add SSR, server endpoints, server adapters, API routes, databases, auth, secrets, or runtime backend dependencies.
- Cloudflare Pages should be able to deploy the static build output directly.
- All mocked interactivity must work locally in the browser with static assets and client-side JavaScript only.
- Keep `bun check` clean before finishing code changes.
- Run `bun run build` before finishing substantial implementation changes unless the change is documentation-only or there is a clear blocker.
- Do not introduce new libraries unless there is a concrete need that Astro, Tailwind, Starwind, Astlide, or vanilla JS cannot cover.

## Tech Stack Rules

- Use Astro as the primary framework.
- Use Tailwind CSS v4 through the existing `@tailwindcss/vite` setup.
- Use `src/styles/starwind.css` as the CSS-first theme and token source.
- Use Starwind UI as the design-system base. Components added by Starwind should live under `src/components/starwind/`.
- Prefer Astro components and vanilla JS. Do not add React, Vue, Svelte, or other client frameworks unless explicitly justified.
- Use `@astlide/core` for the presentation deck.
- Use `@tabler/icons` only when icons are useful and do not replace simple CSS/SVG treatments.

## Repository Architecture

Prefer this structure as the project grows:

- `src/layouts/BaseLayout.astro` for the shared HTML shell, metadata, and `starwind.css` import.
- `src/components/` for reusable project components.
- `src/components/starwind/` for components generated by Starwind CLI.
- `src/data/fiberloop.ts` or `src/data/fiberloop.json` for shared mock stats, product copy, app states, and demo data.
- `src/pages/index.astro` for the promotional website.
- `src/pages/mobile.astro` for the mobile app mock unless the user chooses a different route.
- `src/content.config.ts` for Astlide content collections once the deck is implemented.
- `src/content/decks/fiberloop/` for the Astlide presentation files.
- `public/` for static assets that should be copied as-is.

Keep routes simple and demo-friendly. The preferred initial routes are `/` for the promotional website and `/mobile` for the app mock.

## FiberLoop Content Canon

Use the project PDF as the source of truth for the concept. Key points:

- The environmental problem is water and air contamination by textile microplastics released during synthetic-clothing wash and dry cycles.
- The source is everyday and usually invisible, which makes it strong for visual storytelling.
- FiberLoop captures microfibers before they reach sewage, storm drains, water treatment systems, rivers, or outdoor air.
- The domestic version connects to a washing-machine drain hose or compatible dryer/lavasecarropas exhaust path.
- Larger versions can target laundromats, hotels, hospitals, institutions, commercial laundry, and textile industry pilots.
- Sensors monitor filter saturation, flow, and obstruction risk.
- The app shows filter status, estimated captured material, replacement history, nearby collection points, QR registration, and rewards.
- Municipal programs can manage collection points, incentives, subsidies, aggregate statistics, and policy pilots.
- Recovered fibers can be framed as circular-economy input for new materials.
- The initial measurable goal from the PDF is a 25% reduction in microfiber release in participating pilot homes, buildings, or institutions during the first year.

Do not claim FiberLoop is already deployed or scientifically validated. Present it as a prototype, pilot, concept, estimate, or mock when appropriate.

## Brand And Visual Direction

The visual language should feel like clean environmental technology, not a generic startup template.

- Use deep water tones, graphite/neutrals, cyan, blue, green, and occasional warm reward accents.
- Use fiber, water-flow, mesh, filtration, cartridge, sensor, QR, and circular-economy motifs.
- Prefer glassy panels, subtle grain, flowing lines, layered gradients, translucent cards, and technical diagrams.
- Avoid generic purple gradients, stock-looking SaaS sections, interchangeable AI landing-page layouts, and dense walls of text.
- Motion should communicate water flow, fiber capture, cartridge filling, sensor pulses, QR scanning, map pins, and progress toward rewards.
- Respect reduced-motion preferences with `motion-reduce:*` utilities or CSS `prefers-reduced-motion` rules for strong animation.

## Content Rules

- Write user-facing copy in Spanish unless the user requests otherwise.
- Keep presentation slides light on text; put detail in speaker notes.
- Centralize invented promotional stats in shared data and label them as mock/demo in code comments or naming.
- If using real public data, include a visible source in the UI or a nearby source note.
- Prefer the sources cited in the PDF for real claims: UNEP, European Environment Agency, IUCN, Ellen MacArthur Foundation, and the cited academic papers.
- Keep all claims plausible. Avoid absolute statements like “elimina todos los microplásticos”. Use “reduce”, “captura”, “estima”, “piloto”, and “mitiga”.

## Presentation Mock Guidelines

Use `@astlide/core` for a 10-minute class presentation.

When implementing Astlide:

- Add the Astlide integration to `astro.config.mjs`.
- Add `src/content.config.ts` with an Astlide decks collection using `slideSchema`.
- Place the deck under `src/content/decks/fiberloop/`.
- Use `slideLayout`, not `layout`, because Astro MDX reserves `layout`.
- Use `Fragment` for step-by-step reveals.
- Use `Notes` for presenter notes and the oral script.
- Keep slide text minimal and visual-first.
- Keep the deck style aligned with the promotional website.

Suggested 8 to 10 slide arc:

1. Portada: FiberLoop and the invisible pollution problem.
2. Problema: synthetic clothing sheds microfibers in each wash/dry cycle.
3. Escala: public data and mock impact framing.
4. Solución: what FiberLoop is.
5. Funcionamiento: filter, cartridge, sensors, app.
6. App: filter status, QR, rewards, collection points.
7. Impacto medible: captured grams, cartridges, reduction target, pilot metrics.
8. Viabilidad: homes, laundromats, municipalities, manufacturers.
9. Riesgos and mitigations: e-waste, privacy, maintenance, access.
10. Cierre: why acting at the source matters and where the demo continues.

## Promotional Web Guidelines

The promotional web page should sell FiberLoop while making the environmental problem understandable.

Recommended sections:

- Hero with a clear promise and strong visual metaphor.
- Insight/stat cards showing the scale of microfiber leakage.
- “Cómo funciona” in three or four steps.
- Product visualization: device, cartridge, sensors, app, QR, and collection loop.
- Use cases: hogar, lavadero, municipio, industria textil.
- Rewards and municipal collection story.
- Environmental impact dashboard with mock metrics.
- CTA linking to the mobile mock and presentation deck when available.

Design requirements:

- Fully responsive on desktop and mobile.
- Use semantic sections and headings.
- Make data visually scannable.
- Use CSS/SVG for diagrams when possible.
- Keep performance tight: avoid heavy assets and unnecessary JavaScript.

## Mobile Mock Guidelines

The mobile mock should simulate the app experience in a phone frame.

- Preferred route: `/mobile` unless the user chooses another route.
- On desktop, show a centered phone frame with surrounding context.
- On actual mobile screens, make the experience usable full-width without requiring the decorative frame.
- Target a 390x844-ish app viewport, but keep it responsive.
- Use static mock state and vanilla JS for interactions.
- No backend, network dependency, or persisted user account is needed.

Recommended app screens or tabs:

- Dashboard with filter status and captured microfibers.
- Cartridge detail with saturation percentage and replacement warning.
- History of washes, cartridge replacements, and recovered grams.
- Map/list of collection points.
- Rewards progress and municipal benefits.
- QR/cartucho flow with a simulated scan or registration state.

Recommended microinteractions:

- Filter progress filling.
- Sensor pulse or flow animation.
- Tab transitions.
- QR scan shimmer.
- Reward progress increment.
- Alert state for near-full cartridge.

## Accessibility, Quality, And Performance

- Use semantic HTML first.
- Use real buttons for actions and real links for navigation.
- Keep visible focus states.
- Ensure color contrast remains readable in both light and dark surfaces.
- Add `aria-label` where icon-only or visually abstract controls need names.
- Avoid putting essential information only in animation, color, or decorative graphics.
- Use `loading="lazy"` for non-critical images if images are added.
- Keep JavaScript small and local to the page/component that needs it.
- Avoid layout shifts in hero, mobile frame, and slide visuals.

## Implementation Workflow

Before starting substantial work:

- Read this file.
- Read `Document.pdf` or an extracted text version if available.
- Inspect `package.json`, `astro.config.mjs`, `starwind.config.json`, and `src/styles/starwind.css`.
- Check existing pages, layouts, components, and data before inventing new structure.

While implementing:

- Make the smallest correct change that moves the mock forward.
- Preserve user changes and do not revert unrelated work.
- Use `apply_patch` for manual edits.
- Keep shared copy and mock metrics centralized when multiple surfaces need them.
- Prefer reusable Astro components only when reuse is real.
- Do not add backward compatibility code unless there is a concrete reason.

Before finishing:

- Run `bun check`.
- Run `bun run build` for substantial code/UI changes.
- Review the diff for accidental formatting churn, unrelated changes, or leaked secrets.
- Review whether anything learned during the iteration should improve this `AGENTS.md`; update it when useful.
- Report what changed, what was verified, and any known limitations.

## Research Guidance

- Use Context7 or web research when current API details are needed for Astro, Astlide, Tailwind, Starwind, Cloudflare Pages, or cited environmental data.
- Do not guess library-specific conventions when documentation is available.
- For Astlide, remember the key conventions: MDX decks, `_config.json`, `slideLayout`, `Fragment`, `Notes`, presenter mode, and theme/plugin support.
- For Starwind, remember components are copied into the repo and become project-owned code.
- For Tailwind v4, prefer CSS-first configuration through `@theme` in `src/styles/starwind.css`.
